# DB 규칙

본문은 [`db/README.md`](../../../db/README.md)에 있다. 여기서는 코드를 쓸 때 바로 걸리는 것만 요약한다. 왜 Flyway 대신 이 방식인지는 결정 004.

- 엔티티를 바꾼 PR에는 `db/ddl/NNN_#이슈번호_설명.sql`을 하나 추가한다. PostgreSQL 문법. 여러 변경이어도 PR 하나면 파일 하나
- 이미 `develop`에 들어간 SQL 파일은 고치지 않는다. 되돌릴 때도 새 번호로 추가한다
- 번호가 겹치면 나중에 머지되는 쪽이 rebase하면서 올린다
- 테스트는 이 폴더의 SQL로 DB를 만들고 `ddl-auto: validate`로 엔티티와 대조한다. 컬럼 타입과 길이가 엔티티와 어긋나면 컨텍스트 로딩에서 실패한다
- 운영과 개발 서버에는 자동 적용하지 않는다. 배포 전에 번호 순으로 직접 실행한다

## SQL 작성

- 파일 첫 줄에 파일 이름, 둘째 줄부터 무엇을 왜 바꾸는지 한두 줄
- FK 이름은 `fk_<테이블>_<컬럼>`, unique index는 `uk_<테이블>_<컬럼들>`, 일반 index는 `idx_<테이블>_<컬럼들>`
- enum 컬럼은 `varchar(30)`에 `check ((col in ('A', 'B')))`를 건다. 값이 늘면 새 SQL에서 제약을 다시 만든다
- 시각 컬럼은 `timestamp(6)`
- JPA로 표현할 수 없는 제약(부분 unique index 등)은 SQL에만 넣고 주석에 그렇게 적는다

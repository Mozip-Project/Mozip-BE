# DB 규칙

본문은 [`db/README.md`](../../../db/README.md)에 있다. 여기서는 코드를 쓸 때 바로 걸리는 것만 요약한다. 왜 Flyway 대신 이 방식인지는 결정 004.

- 엔티티를 바꾼 PR에는 `db/ddl/#이슈번호_설명.sql`을 하나 추가한다. PostgreSQL 문법. 여러 변경이어도 PR 하나면 파일 하나
- 이미 `develop`에 들어간 SQL 파일은 고치지 않는다. 되돌릴 때도 새 파일로 추가한다
- 적용 순서는 파일명 사전순(= 이슈번호)이다. 같은 이슈에서 파일이 여러 개면 설명을 알파벳순으로 짓는다. 다른 브랜치가 같은 테이블을 같은 `create table`로 다시 만들어 머지 시점에 충돌하면, 먼저 `develop`에 들어간 쪽을 그대로 두고 나중 쪽을 `alter`로 바꿔 쓴다 (결정 004 변경 기록 2026-11-23)
- 테스트는 이 폴더의 SQL로 DB를 만들고 `ddl-auto: validate`로 엔티티와 대조한다. 테이블이나 컬럼이 없거나 타입이 다르면 컨텍스트 로딩에서 실패한다
- validate는 varchar 길이, nullable, check 제약을 비교하지 않는다. 이 셋은 리뷰에서 엔티티 어노테이션과 직접 맞춰 본다
- 운영과 개발 서버에는 자동 적용하지 않는다. 배포 전에 머지된 순서대로 직접 실행한다
- 이미 돌고 있는 DB에는 `#36_baseline` baseline을 건너뛰고 그 다음 파일부터 실행한다
- dev는 `ddl-auto: update`라 배포가 먼저 되면 Hibernate가 컬럼을 먼저 만든다. 그래서 컬럼과 인덱스는 `if not exists`로 쓰고, 제약을 지울 때는 Hibernate가 붙인 이름일 수 있어 실제 이름을 확인한다

## SQL 작성

- 파일 첫 줄에 파일 이름, 둘째 줄부터 무엇을 왜 바꾸는지 한두 줄
- FK 이름은 `fk_<테이블>_<컬럼>`, unique index는 `uk_<테이블>_<컬럼들>`, 일반 index는 `idx_<테이블>_<컬럼들>`
- enum 컬럼은 `varchar(30)`에 `check ((col in ('A', 'B')))`를 건다. 값이 늘면 새 SQL에서 제약을 다시 만든다
- 시각 컬럼은 `timestamp(6)`
- JPA로 표현할 수 없는 제약(부분 unique index 등)은 SQL에만 넣고 주석에 그렇게 적는다

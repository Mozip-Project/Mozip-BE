# 운영진의 현재 단체는 프론트가 쿠키로 관리하고, 백엔드는 organizationId 인자와 소속 검사로만 다룬다

- 상태: accepted
- 기록일: 2026-11-20
- 관련: #62, 결정 007을 대체

## 맥락

결정 007에서 현재 단체를 백엔드가 쿠키로 심고 운영진용 GraphQL 필드가 그 쿠키를 읽기로 했다. 그런데 백엔드는 운영진용 요청마다 `organizationId`로 소속을 검사하므로, 쿠키까지 보면 두 값이 어긋날 때 무엇을 믿을지 애매해진다. 현재 단체는 화면이 어느 단체를 띄울지 정하는 UI 상태라 프론트가 들고 있는 것이 자연스럽다고 프론트와 다시 정리했다.

## 결정

- 현재 단체는 프론트가 자기 도메인 쿠키에 단체 id만 저장한다. 단체를 고르는 순간 프론트가 쓰고, 미들웨어가 읽어 운영진 화면과 지원자 화면을 가른다
- 역할(대표자, 운영진)은 쿠키에 넣지 않는다. 프론트가 `me.memberships`에서 쿠키의 단체 id로 찾아 쓴다
- 백엔드는 현재 단체 쿠키를 굽지도 읽지도 않는다. 운영진용 GraphQL 필드는 `organizationId`를 인자로 받고, 요청마다 `OrganizationAccessChecker`로 소속을 검사한다
- 단체 선택과 전환 REST 엔드포인트는 만들지 않는다
- 쿠키가 없거나 쿠키의 단체가 소속에 없을 때 어디로 보낼지(지원자 홈, 첫 단체)는 기획이 정하고 프론트가 구현한다

## 근거

- 백엔드가 어차피 인자로 받은 단체의 소속을 검사하므로, 쿠키를 따로 읽으면 같은 정보를 두 경로로 받는 셈이다. 인자 하나로 통일하면 어긋날 일이 없다
- 단체 전환은 프론트에서 시작한다. 프론트 도메인 쿠키면 서버 왕복 없이 미들웨어가 바로 읽어 응답 속도에 영향이 없다
- `me.memberships`가 단체별 역할을 주므로 역할을 쿠키에 복제하면 역할이 바뀌었을 때 쿠키가 옛 값을 들고 있게 된다. 단체 id만 두면 역할은 항상 서버 응답이 기준이다
- 운영진용 요청에 인자 하나 더 실리는 정도는 정보량 부담이 아니다

## 고려한 대안

- 백엔드가 REST로 쿠키를 심고 GraphQL이 쿠키에서 읽기 (결정 007): 기기를 바꿔도 현재 단체가 유지되지만 웹 서비스라 그럴 일이 드물고, 인자와 쿠키가 어긋나는 경우를 처리해야 한다
- 프론트 쿠키에 단체 id와 역할을 함께 저장: 미들웨어가 역할 기준으로도 라우팅할 수 있지만, 역할이 바뀔 때 쿠키를 갱신하는 코드가 필요하고 memberships와 중복된다. 미들웨어는 운영진 모드 여부만 알면 되므로 뺐다

## 영향 범위

- 결정 002의 REST 범위는 원래대로 인증과 헬스 체크만
- `docs/agent/rules/graphql.md` 인증 항목: 운영진용 필드는 `organizationId` 인자
- `AuthCookieManager`, `auth.cookie` 설정은 현재 단체와 무관. 추가 쿠키 없음
- B의 운영진 기능(members, inviteMember 등)과 A의 운영진용 필드(공고, 지원서, 평가) 모두 `organizationId` 인자를 유지한다
- 프론트는 쿠키 이름, 만료, 기본 라우팅을 자체 결정한다. 백엔드 API 명세에는 나타나지 않는다
